## HUD scale: root cause and completed correction

Native hosts own the user factor: Windows `(192 / DPI) × factor`; macOS `(2 / backingScale) × factor`; Linux `(2 / GDK scale) × factor`. User factors for -50/-30/0/+30/+50 are 0.5/0.7/1/1.3/1.5. Host zoom is therefore not the same thing as the user factor. At the normalized baseline, browser DPR is 2; after user zoom it is `2 × factor`.

The regression was reproduced **before** the shared correction using the shipped HUD in actual WebKit at 1920×1000. At -50%, play SVG physical width remained **0.92552×** baseline while the context menu shrank to **0.68917×**. Native zoom/DPR was already correct. Zooming out enlarged the CSS viewport, increasing responsive `autoScale` from 0.5 to 0.925926 and almost cancelling the requested shrink. Positive zoom reduced the CSS viewport, where `autoScale` hit its existing 0.5 floor, so enlargement remained visible. The menu has different clamp/scale rules.

`updateViewportUiScale` now calculates proportional scale using the baseline viewport: live CSS viewport multiplied by actual `devicePixelRatio / 2`. Actual DPR avoids applying the requested factor before asynchronous native zoom has taken effect. `const userScale = 1` remains unchanged; main user scaling is not duplicated in CSS. Live viewport dimensions still drive overflow and compactness decisions. Existing minimum scales, panel floor 0.72, feedback floor 0.65, Windows host-display floor, source-panel scaling and CSS clamps remain intact. No per-button Linux workaround, CSS rewrite, new thread or native lifetime change was added.

The current upstream shared formula and all three normalization contracts establish a shared source-level defect. Windows/macOS native hosts were not executed in this audit. WebKit source confirms that WKWebView page zoom reaches pageZoomFactor and that LocalDOMWindow DPR includes it: [WKWebView implementation](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebView.mm), [LocalDOMWindow implementation](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/LocalDOMWindow.cpp). These are engine-contract references inspected on the audit date, not substitutes for future native Windows/macOS smoke testing.

At 1920×1080, Standard play physical widths for -50/-30/0/+30/+50 are **24 / 33.59 / 48 / 62.39 / 72 px**. Context menu widths are **186.03 / 248.80 / 346.20 / 425.08 / 491.92 px**. Menus combine page zoom with existing viewport clamps, so their ratios are intentionally not exactly the icon ratios.

## N04: playback inhibition follow-up

The shared intent is `errorMessage == null && (isPlaying || (shouldPlay && isLoading))`. Linux now routes that Boolean into one process-wide, serialized IO owner. The portal requests Idle + Suspend (12); the guarded fallback requires both a ScreenSaver cookie and logind idle/sleep FD. Private connections and explicit release bound ownership to playback/app lifetime. Backend loss permits one event-driven reconnect; unavailable services leave playback usable without polling or power-setting changes. The existing delayed artwork-cache lifecycle is unchanged.

Regression first: the real-session Compose test failed before the implementation because `EnterImmersivePlayerMode(true)` acquired nothing, then passed with acquisition, pause, resume and disposal assertions. The follow-up runs 15 inhibitor tests (14 fake-backend lifecycle/race tests and one GNOME session observer), plus the existing native bridge, HUD-scale, base-configuration and runtime-override suites. Eleven external fixtures also exercise the compiled JNI backend against isolated D-Bus services: early portal Response, denial, timeout, fallback, partial cleanup, absent services, service/bus loss and process-exit cleanup. These fixtures are not shipped or runtime dependencies.

Final validation with Temurin 17 and the existing private mpv runtime: `buildLinuxPlayerBridge`, `compileKotlinDesktop` and `desktopTest --rerun --no-daemon --no-configuration-cache -Pnuvio.linux.nativeSmokeTest=true`, filtered to `LinuxPlaybackInhibitorTest` (15), `LinuxNativePlayerBridgeTest` (29), `LinuxHudUiScaleTest` (6), `LinuxBaseConfigurationTest` (8) and `DesktopMpvRuntimeOverrideTest` (8): **66 passed, 0 failures, 0 errors, 0 skipped; BUILD SUCCESSFUL**. The final GNOME `GetInhibitors` response was empty. The private libmpv was not rebuilt or changed.

The actual application, with a temporary guest profile and local media, acquired a GNOME session inhibitor with flags 12 during playing and intended buffering. Pause, error, Back and app exit left no Nuvio inhibitor; resume/reopen reacquired it. Source replacement, seek, fullscreen/windowed, focus loss/restoration and -30/0/+30 HUD scale retained correct ownership. The external driver invoked real actions/settings; it did not override the shared playback Boolean or HUD snapshots. This validates session ownership on GNOME Wayland with the existing XWayland player, not physical suspend prevention on every desktop. No actual suspend/shutdown or persistent power change was performed.

## Screensaver: full platform trace

Entry chain: Screensaver settings page → shared settings/storage → `Main.kt` installs `DesktopScreensaver`. Windows retains its native idle/foreground probes and gamepad accounting; Linux delegates to `LinuxScreensaver` and `LinuxSessionIdleSource`; macOS still has no installation. Player lifecycle publishes `playerActive`. Linux dimming and input dismissal were manually validated for `84211f74`; settings tests alone do not establish that acceptance.

The Windows implementation polls on a one-second Swing timer, combines GetLastInputInfo with gamepad idle, and has an AWT activity fallback if the native query is unavailable. Mouse/key/wheel activity dismisses the shade; tiny synthetic mouse movements within three pixels of the appearance position are ignored. It renders an owned black `JWindow` at configurable opacity, not photographs, video or an OS screensaver module. Opacity has a 0.02 minimum; fade-in is two seconds and fade-out 250 ms; cursor is blank while shaded.

Defaults are disabled dimming and disabled shutdown, 10-minute browsing/60-minute playback dim delays, and 100% dim opacity. `activeDuringPlayback=false` suppresses both dimming and shutdown on Windows while the player is mounted (`playerActive`, not just `isPlaying`); Linux applies the same mounted-player policy to dimming only, including paused/buffering playback. The optional Windows shutdown delays are 60 minutes browsing/180 minutes playback and then a 30-second white-text cancellation countdown. Shutdown is foreground-gated via native process/window detection, with `window.isActive` fallback. Windows ultimately runs `shutdown.exe /s /f /t 0` and exits; **no shutdown command was run during this audit**. Linux shutdown settings remain stored/displayed but have no action (J08).

The app window must be visible and not iconified. The shade follows its owner's move/resize bounds, including fullscreen bounds and covering the native player child. It is not an all-monitor overlay; moving the owner changes which monitor is affected. Linux reuses the owned shade, opacity and fades, using POPUP type for full owner coverage on XWayland. It maps only while the owner has AWT focus and unmaps on focus loss/minimization; focus return resets app idle. The Linux HUD focus adapter hides native controls while dimmed and restores them after fade-out. Broader compositor/physical mixed-DPI coverage remains acceptance work.

Linux idle backend order is ScreenSaver `GetSessionIdleTime` at the standard then legacy path, optional Mutter `GetIdletime`, optional XScreenSaver on an explicitly identified X11 session, then monotonic app-input fallback. Probes run on a worker; stale samples are discarded and failed services are retried after 60 seconds. Xss is never treated as a global Wayland/XWayland idle clock. Generic Wayland does not guarantee global idle or foreground-process access, and app input can miss events consumed by the native HUD when no session probe is available. Linux uses owner focus for shade visibility, not a global foreground-process service. J07/P07 therefore remain LINUX_PARTIAL / VALIDATION_ONLY; this refresh does not prescribe a replacement backend without session evidence.

Power policy is separate: Linux `EnterImmersivePlayerMode` consumes the shared `keepScreenAwake` intent through a session inhibitor. N04 uses the portal (Idle + Suspend), with a combined ScreenSaver cookie/logind FD fallback; pause, error, teardown and exit release ownership. Linux mpv retains `stop-screensaver=no` to avoid a competing X11 screensaver/DPMS owner. N04 remains LINUX_IMPLEMENTED (`0d9f8905`), independently of the dimming/idle limitations and absent shutdown (J07/J08/P07). See the [Linux README](../composeApp/src/desktopMain/native/linux/README.md#playback-sleepscreensaver-inhibition) for lifetime and failure policy.

## Release and updater audit

Current `composeApp/build.gradle.kts` configures native distributions DMG/MSI/DEB, desktop icon/resources and runtime staging. Windows has DLL/app-image layout and application identity paths; macOS has signing/notarization configuration controlled by optional credentials. Configuration is not proof that a particular published release is signed. Linux has generic DEB configuration and native runtime build integration, but no complete tested three-format distribution pipeline. No Flatpak/AppImage definitions or release GitHub Actions workflow were found. The five existing workflows handle issue/PR/branch maintenance, not release production.

The repository rule remains source application acceptance first, then **DEB, Flatpak and AppImage directly from the same source commit** with reproducible GitHub Actions builds. Do not repackage one format into another. Runtime provenance, redistributable dependencies, WebKit/system requirements, desktop entries/icons, install/uninstall, fresh-host startup/playback and package-owned update policy are prerequisites. This audit neither rebuilt the private media runtime nor implemented packaging.

`AppUpdaterPlatform.desktop.kt` supports Windows only. Shared `AppUpdater` selects Stable/Nightly releases from UmbraProjects/NuvioDesktop/windows-tv-adaptive; desktop assets/ABI are Windows-oriented. The Windows portable path downloads a ZIP, verifies SHA-256, stages files and uses a batch script for replacement/relaunch; reveal uses Explorer. macOS/Linux are unsupported. No Linux updater is hidden behind the shared setting.

Future Linux behavior needs: fork-owned releases; explicit package/version/architecture/channel identity; automatic check with a real check opt-out; manual Check for updates; visible result/notification; and a user-triggered Update action. Current upstream once-per-run automatic check and auto-install preference are not equivalent to that opt-out. AppImage may use self-update only where appropriate; Flatpak delegates to its update mechanism; DEB uses the package/repository path. Do not copy the Windows in-place ZIP swap into package-managed installs. No updater was implemented here.

### Native and desktop-only boundaries outside expect/actual

`NativePlayerBridge` JNI declarations are not expect declarations. Linux exports the closed player functions. The legacy `setMediaSessionMetadata` remains a no-op, but K05 now uses separate LinuxMprisNative JNI exports and the main-player adapter; it is no longer evidence of a missing media-session backend. `forceVideoRedraw` is intentionally a no-op because the VO owns video presentation. Windows-only identity/video-profile/window-chrome/borderless/compact-window interaction, XInput polling, systemIdleMs and isForegroundProcess exports are not ported under those signatures. macOS also lacks those Windows-specific helpers. Linux has separate shader application and LinuxIdleNative queries; J07/P07 retain global-idle/foreground limitations. Inspected callers gate the Windows-only functions; absence must not be treated as an unconditional Linux linker failure. PiP, input and remaining platform rows capture the actual gaps.

Desktop-only services such as DesktopScreensaver, GamepadInput, Main tray/drag-drop/window restore, GameFolderScanner/GameLauncher, DesktopStorage, NuvioEngineLibrary, native shader/SVP discovery and packaging are covered separately in the master matrix and detailed traces. Compile-time expect/actual completeness alone would miss these gaps.
